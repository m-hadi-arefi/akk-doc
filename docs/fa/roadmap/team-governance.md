# حاکمیت فنی، نقش رهبری و تیم اولیه توسعه

یکی از دلایل شکست پروژه‌های تحول دیجیتال، استخدام تیم‌های بزرگ و پرهزینه پیش از استقرار زیرساخت‌های مهندسی است. در آرین خودرو، استراتژی نیروی انسانی بر پایه **یک تیم جمع‌وجور، بسیار چابک و با بازده بالا** تنظیم شده است.

---

## ۱. ساختار تیم فنی فاز اول و دوم

تیم اجرایی اولیه از ۳ نفر کلیدی تشکیل می‌شود:

```text
┌────────────────────────────────────────────────────────┐
│               معمار ارشد سیستم (Lead Architect)        │
│    • راهبری فنی کلان و طراحی سکوی مرکزی                 │
│    • تدوین استانداردهای کدنویسی، امنیت و بازبینی معماری │
│    • مذاکره فنی با مدیران ارشد و مالکان فرایند          │
└───────────────────────────┬────────────────────────────┘
                            │
            ┌───────────────┴───────────────┐
            ▼                               ▼
┌───────────────────────────────┐ ┌───────────────────────────────┐
│ برنامه‌نویس سطح میانی ۱ (Mid 1)│ │ برنامه‌نویس سطح میانی ۲ (Mid 2)│
│ • تمرکز: Backend & APIs       │ │ • تمرکز: Full-Stack & UI      │
│ • آداپتور تادارک و سرویس هویت │ │ • داشبوردها و پورتال‌های وب   │
└───────────────────────────────┘ └───────────────────────────────┘
```

---

## ۲. شرح وظایف و ماتریس مسئولیت‌ها (RACI)

| فعالیت / خروجی | معمار ارشد | توسعه‌دهنده ۱ (Backend) | توسعه‌دهنده ۲ (Full-Stack) | مدیرعامل / حامی پروژه |
| :--- | :--- | :--- | :--- | :--- |
| **طراحی معماری Core Platform** | **A / R** (مسئول اصلی) | C (مشارکت) | C (مشارکت) | I (مطلع) |
| **پیاده‌سازی آداپتور دلفی تادارک** | A (تأییدکننده) | **R** (پیاده‌ساز) | C (تست و اتصال) | I (مطلع) |
| **پیاده‌سازی داشبوردهای کاربری و CRM** | A (تأییدکننده) | C (تأمین API) | **R** (پیاده‌ساز) | C (دریافت بازخورد) |
| **تایید تصمیمات معماری (ADR)** | **A / R** (نهایی‌ساز) | C (پیشنهاددهنده) | C (پیشنهاددهنده) | I (آگاهی از اثرات تجاری) |

---

## ۳. ریتم کاری و فرآیندهای چابک تیم

1. **اسپرینت‌های دوهفته‌ای (2-Week Sprints)**:
   در پایان هر دو هفته، یک نسخه قابل آزمایش و ارزش‌محور (Working Increment) تحویل داده می‌شود.
2. **بازبینی اجباری کد (Mandatory Peer Review)**:
   هیچ کدی بدون بررسی معمار ارشد و بررسی تست‌های خودکار به خط اصلی (Main branch) مرج نمی‌شود.
3. **ثبت رسمی تصمیمات معماری (ADR)**:
   تغییرات کلان پایگاه داده، الگوهای اتصال سامانه‌ها یا کتابخانه‌های کلیدی به صورت مکتوب در قالب ADR ثبت می‌گردند.
