# مرحله ۱۴: استانداردهای توسعه و دستورالعمل‌های مهندسی

## هدف و دامنه شمول
استقرار یکپارچگی مهندسی، انضباط سورس‌کد، مدیریت شاخه‌های گیت و دقت در آزمون‌ها در تمامی پروژه‌های نرم‌افزاری شرکت آریان خودرو.

## استانداردهای بنیادین مهندسی

### ۱. مدل شاخه‌بندی گیت و پیام‌های کامیت
- **مدل شاخه‌بندی**: استفاده از **Trunk-Based Development** برای سرویس‌های سریع (شاخه‌های فیچر با عمر کوتاه که روزانه از طریق PR ادغام می‌شوند) یا **Git Flow** برای نسخه‌های زمان‌بندی‌شده سازمانی.
- **انضباط کامیت‌ها**: پایبندی سخت‌گیرانه به استاندارد **Conventional Commits**:
  - `feat(auth): add OAuth2 token revocation endpoint`
  - `fix(workshop): resolve race condition in repair order state`
  - `refactor(pricing): decouple commission calculator from database`

### ۲. استانداردهای بازبینی کد و درخواست‌های ادغام (Pull Requests)
- هر درخواست ادغام (PR) باید الزامات زیر را برآورده سازد:
  ۱. لینک به تسک سیستم مدیریت وظایف یا نیازمندی تجاری مرتبط.
  ۲. شرح شفاف تغییرات اعمال‌شده و ارزیابی ریسک‌های احتمالی.
  ۳. کدهای تست خودکار جدید برای راستی‌آزمایی تغییر.
  ۴. قبولی کامل در خط CI (بیلد موفق، پاس شدن تست‌ها، صفر خطای لینتر).
  ۵. تاییدیه رسمی حداقل یک سرپرست فنی (Tech Lead) یا مهندس ارشد.

### ۳. هرم آزمون‌های خودکار (Testing Pyramid)
```text
        ▲
       / \        آزمون‌های سرتاسری (۱۰٪ - جریان‌های حیاتی کاربر)
      /   \
     /─────\      آزمون‌های یکپارچگی (۳۰٪ - قراردادهای API و پایگاه داده)
    /       \
   /─────────\    آزمون‌های واحد (۶۰٪ - منطق خالص دامنه کسب‌وکار)
```

## هوش مصنوعی در این مرحله

### کمک هوش مصنوعی (AI Assistance)
- **بازبینی خودکار کدهای PR**: بررسی نام‌گذاری متغیرها، اصول کد تمیز و رعایت استانداردهای فرمت‌بندی در درخواست‌های ادغام.
- **تضمین مستندسازی کدها**: کنترل اینکه اینترفیس‌های عمومی، کلاس‌ها و کنترلرهای REST دارای کامنت‌های توضیحی معتبر باشند.
- **پایش سلامت کتابخانه‌ها**: بررسی وابستگی‌های نرم‌افزاری برای شناسایی بسته‌های قدیمی یا هشدارهای امنیتی.

### تصمیم‌گیری انسانی (Human Decision)
- **تکامل استانداردهای تیم**: تدوین و ارتقای شیوه‌نامه‌های کدنویسی، مدل‌های شاخه‌بندی گیت و قواعد اختصاصی لینتر.
- **تصویب استثناهای معماری**: موافقت با انحرافات موجه از الگوهای رایج در شرایط خاص تجاری یا محدودیت‌های زیرساخت.

### تأییدیه انسانی (Human Approval)
- **تأییدکنندگان الزامی**: سرپرست صنف مهندسی (Guild Lead) و مهندسان ارشد نرم‌افزار.

### ریسک‌ها (Risks)
- **لینتینگ افراطی و فلج‌کننده**: اعمال قواعد ظاهری و بسیار سخت‌گیرانه که بدون ارتقای پایداری نرم‌افزار، سرعت تحویل تیم را کُند کند.
- **غفلت از عیوب ریشه‌ای معماری**: تمرکز مفرط جلسات بازبینی بر فرمت ظاهری کدها به جای توجه به باگ‌های ساختاری و معماری.

### شواهد الزامی (Required Evidence)
- گزارش‌های قبولی پایپ‌لاین تحلیل ایستای کد و لینتر در CI/CD.
- دستورالعمل‌های مصوب شاخه‌بندی گیت و چک‌لیست بازبینی سورس‌کد.
- کاتالوگ استانداردهای مهندسی و الگوهای کدنویسی سازمان.
